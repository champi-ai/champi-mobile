## [Unreleased]

### Added
- `RemoteSttProvider` and `RemoteTtsProvider` (`:providers:remote`, issue #33) — transport stubs that implement `SttProvider` and `TtsProvider` respectively with `locality = REMOTE`. Both return `available() = false` always (voice-over-remote transport is deferred; a `// TODO(transport):` comment explains the gap) and emit an empty flow from `transcribe`/`synthesize` so callers receive no output and do not throw. Capabilities reflect a plausible remote service profile (`languages = ["en","es"]`, `supportsStreaming = true`). Both are registered in `ProvidersRemoteModule` via `@Binds` following the same pattern as `RemoteLlmProvider`. Unit tests verify `available() == false`, `locality == REMOTE`, non-placeholder capability values, and empty-flow output for both stubs without requiring an Android context or Hilt graph. On-device `EdgeLlmProvider` (issue #18) remains intentionally deferred; the routing policy receives a `List<LlmProvider>` containing only `RemoteLlmProvider` for now.
- `EdgeSttProvider` (`:providers:edge`, issue #26) — on-device STT backed by Android's `SpeechRecognizer` API. On API 31+ (Android 12), `SpeechRecognizer.createOnDeviceSpeechRecognizer` is used to guarantee audio never leaves the device; `RecognizerIntent.EXTRA_PREFER_OFFLINE = true` is always included as a belt-and-suspenders measure. `available()` returns `true` only on API 31+ when `SpeechRecognizer.isOnDeviceRecognitionAvailable` confirms an on-device model is present, and `false` otherwise — on API < 31 the default recognizer can silently fall back to a cloud backend, which violates the V1 never-off-device requirement. There is no download flow this app controls (unlike the LLM/#18 pattern): on-device STT models are managed by the Android platform and must be pre-installed (typically via the Google app). The `transcribe(segment: Flow<PcmFrame>)` implementation has an inherent mic re-acquisition tradeoff: `SpeechRecognizer` provides no public API for accepting pre-recorded PCM; it always opens the microphone itself via `startListening()`. The segment flow is drained concurrently to honour the upstream contract, but recognition runs against a fresh mic capture — for short utterances the user may have finished speaking before `startListening` begins. Whisper.cpp (excluded from M3 scope) would not have this limitation. Locale selection maps any Spanish variant to `es-MX` and everything else to `en-US` (the two locales in `capabilities`). Wired into the Hilt graph via the updated `ProvidersEdgeModule`. Unit tests cover the locale-mapping pure function (`localeTagForRecognizer`) for en-US, en-GB, es-MX, es-ES, bare "es", French, and Japanese locales; the instrumented test verifies `available()` matches `isOnDeviceRecognitionAvailable` on API 31+ and returns false on API < 31. Acceptance criteria requiring real speech input (> 90% word accuracy for en-US and es-MX, ≤ 1 s transcription latency, airplane-mode isolation) require a physical device with the Google on-device model installed and cannot be verified in this environment.
- `RoutingSettingsRepository` (`:core`, issue #32) — DataStore-backed routing policy preferences: `edgeOnlyMode` (default `false`) and per-locality provider enable toggles (`edgeSttEnabled`, `edgeLlmEnabled`, `edgeTtsEnabled`, `remoteSttEnabled`, `remoteLlmEnabled`, `remoteTtsEnabled`, all default `true`). Follows the established repository pattern — a dedicated `routing_settings` DataStore file, `@Singleton`-scoped, `@Inject constructor`, `Flow<Boolean>` reads and `suspend set*()` writes.
- `QueuedTurnEntity` + `QueuedTurnDao` (`:core`, issue #32) — Room entity for turns that could not be served because no provider was available. Fields: `id` (autogenerate Long), `conversationId`, `inputText`, `inputAudioPath?`, `enqueuedAt` (epoch millis), `retryCount` (default 0). `QueuedTurnDao` exposes `insert`, `getOldest` (single oldest row by `enqueuedAt`), and `delete`. Registered in `AppDatabase` (schema version bumped 2→3 with `MIGRATION_2_3` creating the `queued_turns` table), `QueuedTurnDao` provided through `CoreModule` — no second `Room.databaseBuilder` call.
- `EdgeVadProvider` (`:providers:edge`, issue #25) — on-device VAD backed by the bundled Silero VAD ONNX model (`silero_vad.onnx`, ~2.3 MB, MIT-licensed). `segment(audio: Flow<PcmFrame>)` accumulates incoming PCM samples into 512-sample windows (the Silero-required chunk size at 16 kHz), runs ONNX inference per window via ONNX Runtime for Android (scoped to `:providers:edge` only), and emits a `SpeechSegment` for each detected utterance — onset when speech probability ≥ 0.5, endpoint when silence persists past the configurable `endpointingThresholdMs` (default 700 ms). The LSTM states (`h`/`c`) are maintained across windows and reset per `segment()` call. `available()` returns `true` unconditionally once the asset-loaded session initialises (no download step). Wired into the Hilt graph via `ProvidersEdgeModule`. Unit tests cover the onset/silence state machine (including hysteresis, two-utterance separation, flush-at-end) and the re-chunking accumulator for both smaller-than-chunk and larger-than-chunk input frames; criteria requiring real audio hardware (700 ms latency from speech offset, background-noise false-positive rate, airplane-mode isolation) require a physical device and are not verified here.
- `AndroidTtsProvider` (`:providers:edge`, issue #27) — edge TTS backed by the Android platform `TextToSpeech` engine. `synthesize(text: Flow<String>)` splits incoming LLM tokens at `.`/`!`/`?` sentence boundaries, calls `TextToSpeech.synthesizeToFile` per sentence, reads the WAV output back as 16-bit PCM mono `AudioChunk`s (sample rate taken from the WAV header), and emits them in order so the first chunk is ready within ~500 ms of the first sentence completing — keeping the pipeline within the 1.5 s p50 budget. Cancellation (barge-in) calls `TextToSpeech.stop()` from the flow's `finally` block and deletes any in-flight temp WAV files. `available()` checks TTS engine init status and `isLanguageAvailable` for en-US and es-MX. Wired into the Hilt graph via the updated `ProvidersEdgeModule`. Instrumented tests cover `available()`, single-sentence synthesis, multi-sentence chunking, and the cancellation contract; the AudioTrack leak check (repeat cancel-and-replay under Android Profiler) requires a physical device and manual verification.
- Long-press quick-actions: `attention` wiring and release-on-target fix (`:overlay`, issue #13). The bubble `Box` and its `pointerInput(Unit)` block now occupy the same structural position in the Compose tree for both `COLLAPSED` and `QUICK_ACTIONS` modes (merged into a single `else` branch of the mode switch), so Compose preserves the pointer-stream coroutine across the COLLAPSED→QUICK_ACTIONS window resize — the same technique already used for the drag/dismiss full-screen expansion. Post-long-press finger movement calls `AppStateHolder.setAttention` with a value proportional to the finger's distance from the bubble centre relative to the 96 dp arc radius (0 = at centre, 1 = at/beyond the arc). Release position is compared against each target's geometry via a new `quickActionsHitTest` function (dispatches to `radialArcHitTest` or `edgeRailHitTest`; each target has a 24 dp hit radius for the radial arc); releasing over a target fires its action, releasing elsewhere cancels with no side effect. `attention` is reset to 0 when the mode leaves `QUICK_ACTIONS` via either the gesture path or the TalkBack `clickable` path. A `!longPressFired` guard was also added to the drag-start check so a post-long-press finger slide drives `attention` instead of incorrectly starting a drag
- Dismiss zone visual and peek-state tap fix (`:overlay`, issue #11): a 120 dp × 64 dp bottom-center target is rendered over the full-screen window whenever a drag is active; it highlights in the error colour when the bubble centre enters the detection zone, and releasing there animates the bubble off the bottom of the screen before removing the overlay (service continues running). Tapping a peeked bubble now restores full visibility without also opening the conversation panel. The peek idle timer now resets on every gesture (tap, drag, long-press) via a `gestureCount` key on the LaunchedEffect, not only when `bubbleOffset` or `mode` changes; changing `peekMinutes` to 0 takes effect immediately because `peekMinutes` is now also a LaunchedEffect key

- Wired the two remaining radial quick-action buttons (`:overlay`) that were stubbed pending `:audio`: mute mic toggles a persisted `OverlayPreferencesRepository.micMuted` flag; push-to-talk toggles a real `AudioCapture.pcmFlow()` collection, driving `AppState.audioLevel` from live RMS amplitude and `CharacterState.LISTENING`. Push-to-talk while muted, or without `RECORD_AUDIO` granted, briefly flashes `CharacterState.ERROR` instead of starting. `MainActivity` gained an optional mic-permission request button (same pattern as notifications — doesn't block the rest of the app). Verified on real hardware: `dumpsys audio`/`dumpsys` HAL logs show a genuine `AudioPolicyManager` `startInput`/`stop` pair (source `VOICE_RECOGNITION`, 16kHz mono) opening and cleanly releasing on toggle, the bubble visibly changes color per state (blue while listening, red on the muted-refusal flash), and no audio session opens at all while muted

- Real conversation panel message list and input row (`:overlay`, issue #21) — right-aligned user bubbles, left-aligned assistant bubbles, streamed tokens update the same bubble in place, auto-scroll to the newest message only when the user was already near the bottom, send button disabled while a turn is in flight, and the conversation seeds from Room on cold start so a process restart still shows prior history
- Panel header state tag (`:overlay`, issue #22, partial) — shows the live `CharacterState` label ("thinking", "idle", etc.) next to the character; the provider/locality tag this issue also wants is deferred to #15 (Rive `CharacterRenderer` — the current placeholder circle has nowhere sensible to put it)
- Fixed IME avoidance (issue #12): the overlay window previously went completely blank whenever the keyboard opened (`if (imeVisible) return`, a heuristic-detection dead end); replaced with `WindowManager.LayoutParams.SOFT_INPUT_ADJUST_RESIZE` on the (now genuinely focusable) expanded-panel window, verified on-device — the panel correctly shrinks so the input row sits above the keyboard with no overlap, and both `FLAG_NOT_FOCUSABLE` toggling and "usable on top of a running app" (verified over the Alarms app) are confirmed working
- `RemoteLlmProvider` (`:providers:remote`) — a real `LlmProvider` backed by any OpenAI-compatible `/chat/completions` endpoint, configured via `local.properties` (gitignored, never committed) rather than hardcoded. Requests `stream: false`: the target Ollama endpoint returns a full `chat.completion` JSON body with `Content-Type: application/json` even when `stream: true` is requested — a cloud-routed model, discovered by testing on a real device — which a strict SSE client rejects outright. `TurnOrchestrator` also gained a catch for a mid-turn provider failure (network drop, bad response), returning to `IDLE` with an error message instead of leaving the character stuck in `THINKING` — the existing tests only covered the unavailable-before-starting path. Verified end-to-end on a real device: a real chat round-trip through the running Ollama endpoint. Issue #18 (on-device edge model, still open) covers the no-network/no-cost on-device path separately

### Added
- `TurnOrchestrator` (`:assistant`, issue #20) — drives the full text-turn lifecycle: `submitText(input)` persists the user message, sets `CharacterState.THINKING`, streams `LlmProvider` tokens incrementally into `AppStateHolder`'s conversation list (via a new `updateConversationEntry`, not one entry per token), persists the finished assistant message, and returns to `IDLE`. Submitting a second turn mid-stream cancels the first (`cancelAndJoin` before launching the new one) without leaving the character stuck in `THINKING`; an unavailable `LlmProvider` shows an error and recovers within 2 seconds. `AppStateHolder` gained `updateConversationEntry`. Verified on real hardware against a scripted `FakeLlmProvider` test double (real integration is blocked on #18's edge model weights) — all four acceptance criteria pass, including proving cancellation happens before the cancelled turn ever reaches `LlmEvent.Done` (persisted message count stays at 3, not 4)
- `ConversationManager` (`:assistant`, issue #19) — authoritative source for the active conversation: lazily loads the most recent conversation from Room on first use (or creates one), `appendUserMessage`/`appendAssistantMessage`, `clearConversation`, and a `messages: Flow<Message>` that switches to a new conversation's stream via `flatMapLatest` if `clearConversation()` runs mid-collection. `Message` domain model added in `:core`. Verified on real hardware: appending a message then building a second `ConversationManager` against the same on-disk database (simulating a process restart) finds the existing conversation; the `messages` flow observably updates within 100ms of an append
- `ActionSettingsRepository` (`:core`, issue #38, partial — see below) — DataStore-backed `ALARM_ACTIONS_ENABLED`/`CALENDAR_ACTIONS_ENABLED`/`PROACTIVE_RATE_LIMIT_PER_HOUR` (default: both enabled, 3/hr), now wired into `AlarmTimerActionProvider` and `CalendarActionProvider` so disabling either returns a graceful `ToolResult` error instead of scheduling/inserting — this closes the "per-action toggle" acceptance criterion left open on #41 and #42
- Quick Settings tile (`ChampiTileService` in `:app`, issue #38, partial): starts `ChampiService` and requests the conversation panel open via a new `AppStateHolder.requestOpenPanel()` nonce (a `StateFlow` rather than a bare event, so a tap racing service startup still lands instead of being lost). Verified end-to-end on real hardware: `adb shell cmd statusbar add-tile`/`click-tile`, confirmed via `dumpsys activity services` (service started with reason "tile onclick") and a screenshot showing the expanded panel actually on screen. The system-tray proactive notification with `RemoteInput` reply this issue also asks for is deferred — its "reply submitted as a new turn" criterion needs `TurnOrchestrator` (#20) and the rate-limiter (#39), neither built yet — so #38 stays open for that piece
- `CalendarActionProvider` (`:actions`, issue #42, partial — see below) — real `create_event` `ActionProvider`: without `READ_CALENDAR`/`WRITE_CALENDAR`, opens a pre-filled `ACTION_INSERT` calendar-app intent for the user to review and save; with the permission granted, inserts directly into `CalendarContract.Events` and returns `{"status":"created","eventId":<id>}`. Verified on real hardware against the device's actual synced Google calendar account (a real event created and confirmed via `content query`, then deleted by the test itself to avoid leaving data behind). Still blocked on #38 (per-action DataStore toggle) and #40 (the destructive-confirmation dialog this issue explicitly wants in front of every direct insert), so issue #42 stays open for those two acceptance criteria
- `AlarmTimerActionProvider` (`:actions`, issue #41, partial — see below) — real `set_alarm`/`set_timer` `ActionProvider` scheduling via `AlarmManager.setExactAndAllowWhileIdle`, gated on `canScheduleExactAlarms()` on API 31+ with a clear `ToolResult` error when denied instead of silently failing; `AlarmReceiver` posts the firing notification. Verified on real hardware: an instrumented test suite confirms both the success path (a real `RTC_WAKEUP` alarm visible in `dumpsys alarm`, routed to `AlarmReceiver`) and the permission-denied error path, branching on the device's actual exact-alarm grant state rather than toggling it mid-test — mutating that grant against the test's own live process kills it (signal 9), the same failure mode `:audio`'s instrumented tests hit revoking `RECORD_AUDIO`. Still blocked on #38 (per-action DataStore toggle) and #40 (message-list undo card), so issue #41 stays open for those two acceptance criteria
- Spring animation on bubble edge-snap release (issue #10), instead of an instant jump
- `SettingsActivity` (`:app`) — wires the quick-actions Settings target to a real screen: quick-actions geometry (radial arc / edge rail) and peek idle timeout (0-15 min, 0 disables peek), both backed by `OverlayPreferencesRepository`
- Partial TalkBack accessibility (issue #58, remainder blocked on #31/#44 which don't exist yet): bubble now has `contentDescription` plus semantic click/long-click actions mirroring its custom gesture detector, which was otherwise invisible to TalkBack; expanded panel gained a real 48dp "Close panel" button (replacing a 32x4dp non-focusable decorative bar); Settings screen's peek-timeout slider gained a `contentDescription`
- Provider API interface definitions (issue #17) in `:providers:api` — `Provider`/`Locality`/`Cost`/`ProviderCapabilities`, `WakeWordProvider`, `VadProvider`, `SttProvider`, `LlmProvider`, `TtsProvider`, `ActionProvider`, plus their model types (`PcmFrame`, `Transcript`, `Conversation`, `LlmEvent`, `AudioChunk`, `ToolSpec`/`ToolCall`/`ToolResult`) — pure Kotlin, no Android dependencies, unblocking the M2-M5 provider/routing work
- `AudioCapture`/`PlaybackQueue` (`:audio`, issue #23) — shared 16kHz PCM capture/playback wrapping `AudioRecord`/`AudioTrack` that wake word, VAD, STT, and TTS will all depend on; ref-counted so concurrent collectors of `AudioCapture.pcmFlow()` never open a second `AudioRecord` on the same input
- Room database (`:core`, issue #16) — `ConversationEntity`/`MessageEntity`/`MessageDao`, `AppDatabase` wired into Hilt, and `ModelFileStore` for versioned on-disk model paths; schema versioned at 2 from the start specifically to exercise a real migration (`MIGRATION_1_2`), verified with an instrumented `MigrationTestHelper` test against the checked-in schema JSON, all passing on real hardware

### Fixed
- `AudioCapture` only checked `checkSelfPermission` before starting capture — confirmed on real hardware that `AudioPolicyService` can still refuse to actually start the input even when that check passes, leaving the flow silently hung (zero emissions, no error) instead of surfacing anything; now also checks `recordingState` right after `startRecording()` and closes the flow with a `SecurityException` if it didn't actually start. Verified with a new on-device instrumented test suite (`audio/src/androidTest`) — real `AudioRecord` frame emission, the no-second-instance guarantee under concurrent collection, and cancellation stopping emission within ~300ms, all passing on a physical device
- Launching `SettingsActivity` via an implicit intent (custom action + manifest intent-filter) threw `ActivityNotFoundException` despite the filter being correctly registered — apps targeting API 31+ can't resolve implicit intents to a non-exported activity, even within the same app; switched to an explicit intent via `Intent.setClassName`
- The repo's CodeQL "Analyze (java-kotlin)" check had been silently failing on every PR since at least #67 (not a required check, easy to miss) — its default `autobuild` setup couldn't trigger the Kotlin extractor across this multi-module Gradle build; replaced with an explicit workflow that builds the same way `android-ci.yml` does
- `MainActivity` required both overlay and notification permission before starting `ChampiService`, contradicting the spec: denying `POST_NOTIFICATIONS` should omit the visible notification, not block the service from running at all; gated on overlay permission alone
- Expanded panel's collapse-on-tap gesture wrapped the entire content `Column` in `.clickable`, which merges all non-interactive descendant semantics into one TalkBack node — harmless today but a trap for issue #21's future input row; moved onto a dedicated background layer instead
- Expanded panel window never cleared `FLAG_NOT_FOCUSABLE`, so a future text-input row (issue #21) would never be able to receive keyboard focus; `WindowSpec` now carries a `focusable` bit, set for the expanded panel only
- Peek idle timeout was a hardcoded 3-minute constant; now DataStore-backed (`peekMinutes`, default 5, 0 disables peek) and resets on any non-`IDLE` character state, not just gestures (issue #11)
- `AppState` was missing the `attention`/`mood` fields the state-machine spec calls for (issue #9); added with setters on `AppStateHolder` — wiring `attention` to live finger position during quick-actions is left for a follow-up, since it needs the gesture detection restructured from discrete click targets to continuous drag hit-testing
- The initial spring-animation attempt crashed the process: `Animatable.animateTo` needs a `MonotonicFrameClock`, only available on a coroutine scope tied to the Composition, not the plain `CoroutineScope` passed down from `OverlayManager`; now uses a `rememberCoroutineScope()`-backed scope for the animation specifically

### Fixed
- `ChampiService.onStartCommand` now also calls `overlayManager.show()` (previously only `onCreate` did), so relaunching the app after dismissing the bubble actually brings it back
- Overlay dismiss crashed the process: `onDismiss` was calling `hide()` (which removes the view) synchronously from inside that same view's still-executing touch-gesture callback; now deferred via `view.post(...)`
- Radial quick-actions arc used raw dp magnitudes as pixel offsets in `Modifier.offset { IntOffset(...) }`, rendering the arc ~2.5x smaller than intended and putting targets outside their visible tap area
- Quick-actions window (`QUICK_ACTIONS_WINDOW_DP`) was 220dp, too small for the 96dp-radius arc of 48dp buttons (needs ~240dp min), so targets overflowed the window and got clipped at the physical screen edge when the bubble was snapped near a corner; bumped to 280dp and confirmed on-device at the worst-case top-left-corner position
- Screen bounds used for clamping (expanded panel height, quick-actions positioning, drag limits, dismiss zone) were computed from `configuration.screenHeightDp`, the *raw* display height — since this window's y-coordinate is relative to the status-bar-inset parent frame, that left ~120px of slack past the real usable bottom, letting content extend into the nav bar and get clipped there; now subtracts status/nav bar insets to get the actual usable height
